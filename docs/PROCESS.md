PART 3: DOCUMENTATION COMPLETE TIER

1. I aimed to create a simple HTML + Javascript website that functions as a wish list. I wanted to have the following features for it: each item would have details such as image, hyperlink, price, and quantity, entries could be fulfilled through a strike-through, and items could be added or removed onto the list. Another additional feature that I added later on was having the data locally stored on the browser so that the user can save their information on the page even after they leave.

2. I think doing the process of microiterating was better than simply giving a very descriptive, large task for the program to complete in "one step". As the lesson stated, I do think that breaking up a large project into each steps and catching errors along the way is a better and more effective way to complete it as you can make changes and fix things in a easier way.

3 and 5. The following are some of the errors I found in my conversation with Claude. For breaking up the project into steps, I modified it so that the functionality of the website through JavaScript came first, so CSS was moved from step 2 to step 9. I also specified that there should only be front-end user validation for the website. After getting to step 5, I started to error check with Claude as it got into more complicated logic (data callbacks, index attributes, and event delegation). Here, some of the errors it found was user inputs that would break the logic of the lists (NaN, floating point numbers, and quantity minimums), as well as providing feedback if the user did not have anything on their list. After approving those changes I also added images being optional. For step 6, I encountered some bugs such as the form inputs not having a line break/space in between each box, making the UI clunky. After reviewing step 6 changes, there was issues with saved data for the browser, trimming whitespace, error catching for invalid inputs (price must have only 2 decimal points, REGEX numbers, and names) and broken URLs. At step 7 I found an error of a missing $0 total for an empty wish list, and not allowing the user to edit price and quantity after submitting them to the list. After this, some of the issues were floating numbers and DOM/JSON updating. At step 8, some of the issues were accessibility text for the inputs, and simple input validation for blank inputs. I found at step 9 there was an error of the user input not automatically "refreshing" if the user fixed an initial wrong input (ex: putting 3 decimal points and then fixing it broke the item submission). After reviewing bugs, Claude found that there was no fixed image and form heights, optional image disables submit, font family and inline spacing was inconsistent, local storage errors, double submit errors, and redundant code. This was the final check after creating the website.

4 and 6. I thought that an issue with Claude Web was that after submitting tasks and changes to Claude Web, I had to download the repo from online to my local PC, and then pull every change from online GitHub to my PC to see the project, as opposed to doing the opposite, making changes on my PC and then uploading changes to the repo. So I prefer terminal Claude because of the this annoying feature, if I was creating a difficult application. A benefit I liked was that I didn't have to open my own compiler, and also I could select what repo I wanted to use on the browser before starting the project, so I didn't have to manually set up my repository.

7. I personally think that microiterations are very useful for big prompts, such as creating websites or applications from scratch. I don't think it would make sense to use this technique if the user already has a skeleton of the project and just wants small tweaks and feedback (CSS, validation, etc.) from Claude to improve the already existing task.
